# ytk Interest Profile — Fact-Check and Literature Sweep: Final Report

Date: 2026-07-17. Scope: claims from the explanation of ytk's interest profile (embedding clustering -> weighted themes -> XML profile at `me/profile.md`), plus four literature sweeps, merged with attention to GitHub issue #83 (interest stock market visualization).

## 2. Missed work, ranked by importance to ytk

1. **LLM-TUP — Temporal User Profiling with LLMs** (https://arxiv.org/abs/2508.08454). The closest published architecture to ytk's entire pipeline: timestamp-split histories rendered as LLM-written prose profiles, embedded and fused. Directly suggests ytk's cheapest temporal upgrade: dual short-term/long-term centroids per theme rather than a single decayed blend. Corroborated by https://arxiv.org/html/2511.00176v1.
2. **BUMP — Self-supervised User Profile Generation** (https://arxiv.org/abs/2606.05336). Its bidirectional eval — score a prose profile by how well it ranks the user's own held-out items — is a ready-made, annotation-free offline eval for ytk's portrait. ytk currently has no way to measure whether `me/profile.md` is any good; this is the recipe.
3. **GISTBench — evidence-based interest verification** (https://arxiv.org/abs/2603.29112). Defines Interest Groundedness (precision vs fabricated interests, recall vs engagement evidence) and Specificity. Combined with personas-2026's persona-evidence alignment, this is the template for making every portrait claim cite the vault items behind it.
4. **Adaptive Collaborative Filtering with Personalized Time Decay** (RecSys '23, https://arxiv.org/abs/2308.01208). The canonical recency-decay mechanism; composes multiplicatively with the Hu/Koren/Volinsky weighting ytk already uses: w = (1 + alpha*r) * exp(-lambda*age). No 2026 paper applies this to personal content libraries — open territory.
5. **Co-Authoring the Self / "Productively Wrong"** (https://arxiv.org/abs/2510.08930, UMAP 2026 follow-up). 8-week, 1,775-user field study of an editable NL interest profile; even wrong AI summaries provoke useful corrections. The empirical blueprint for a profile-edit loop in the hub — the missing half of the Radlinski scrutability story ytk already cites.
6. **Pinterest's PinnerSage successor** (KDD 2025, https://arxiv.org/abs/2506.23060). Replaces offline Ward+medoid with a learned Differentiable Clustering Module. Needs training data ytk doesn't have — it *legitimizes* rather than obsoletes ytk's offline cluster-then-summarize pattern at n=100-1000.
7. **HorizonBench** (https://arxiv.org/abs/2604.17283) and **AlpsBench** (https://arxiv.org/abs/2603.26680). Converging evidence with StreamProfileBench: profile *updating* is the universal LLM failure mode (best model 52.8%; over a third of failures pick the user's original stated preference). ytk's refresh prompt must explicitly instruct superseding of old theme evidence.
8. **GPR4DUR — density-based user representation** (https://arxiv.org/abs/2310.20091). The main published critique of point representations (centroid or medoid): attach a spread/confidence to each theme, not just a bare vector. Cheap to adopt (per-theme covariance or mean pairwise distance) and it feeds #83's confidence bands.
9. **ACL 2026 Findings — Adaptive multi-interest modeling with LLMs** (https://aclanthology.org/2026.findings-acl.117/). Directly attacks fixed-k heuristics like sqrt(n/2): let semantic structure (LLM-merged clusters) choose the theme count. Practitioner consensus for 100-1000 docs is density-based auto-k (UMAP+HDBSCAN) — which ytk's map already uses elsewhere.
10. **Memory Retrieval for Changing Preferences** (https://arxiv.org/abs/2606.02976). Bayes-factor retrieval beats embedding similarity under drift — a challenge to the assumption that weighted theme centroids stay good query vectors as interests shift. Watch-list rather than act-now.
11. **MemPrivacy** (https://arxiv.org/abs/2605.09530) and the personalized-agents survey (https://arxiv.org/abs/2602.22680). Relevant if profile synthesis ever calls a remote model over vault content; the survey is orientation, not action.

## 3. Issue #83 — theme identity across snapshot re-clusterings

The issue's stated hard problem — "price = rolling interest weight" is a lie if each re-clustering reshuffles which cluster is which — is a solved problem class with a 20-year literature. Recommendations, in order of applicability:

**Do not refit independently per snapshot.** The canonical fix is evolutionary clustering (Chakrabarti, Kumar, Tomkins, KDD 2006, https://faculty.mccombs.utexas.edu/deepayan.chakrabarti/mywww/papers/kdd06-evolutionary.pdf): optimize snapshot quality *plus* a history cost penalizing deviation from the previous fit. Chi et al. (KDD 2007, https://dennyzhou.github.io/papers/evospe.pdf) formalize the two regularizers to choose between: PCQ (preserve cluster quality) and PCM (preserve cluster membership). For #83, PCM is the right choice — the ticker cares about *membership* continuity. Practically: seed each refit with the previous snapshot's centroids and add a penalty on centroid movement, or match post-hoc (next point).

**Model theme lifecycle events explicitly.** TextLuas (https://arxiv.org/pdf/1502.04609) matches clusters across snapshots by member composition (Jaccard on item sets) and labels births, deaths, splits, merges, and survivals. A stock-market UI has natural vocabulary for exactly these: IPO (new theme), delisting (dead theme), merger/spin-off (merge/split). Rendering these as first-class events is more honest than forcing every theme into a continuous price line — and it turns the hard problem into a feature. DTECT (https://arxiv.org/pdf/2507.07910) is a 2025 end-to-end template: semantic alignment of topics across consecutive slices plus prevalence-over-time stream/line views.

**Instrument identity drift.** From the dynamic-topic-model evaluation literature (https://arxiv.org/pdf/2508.00710): track Jaccard overlap of a theme's top exemplars between distant snapshots and the fraction of new members per update. When drift crosses a threshold, the ticker's price history is no longer about the same thing — surface that (e.g., a "restated" marker) rather than silently continuing the line.

**Anchor identity on medoids, not centroids.** PinnerSage's medoid rationale (stable item id, robust to outliers, interpretable) transfers directly: a theme's identity across refits is better anchored by "does it still contain these exemplar items" than by centroid distance, which drifts with every added embedding.

**Does the decay/streaming work change the price-series design? Yes, in two ways.**
- *Price definition:* raw theme weight over-retains — the same conservative bias StreamProfileBench documents in LLMs (https://arxiv.org/abs/2605.25758) exists in any cumulative weight. Price should be the recency-decayed weight, w = (1 + alpha*r)*exp(-lambda*age) summed over theme members (https://arxiv.org/abs/2308.01208), so themes the user stopped feeding actually decline. Volume (ingestion count per interval) is already decay-free and stays as specified.
- *Two lines per ticker:* the LLM-TUP / stage-wise-subgraph line (https://arxiv.org/abs/2508.08454, https://arxiv.org/abs/2603.10471) suggests plotting long-term weight and a short-window weight separately — their divergence *is* the trend signal ("rising" = short > long), replacing any need for ad-hoc momentum heuristics and making the LLM's "why is this theme rising" narration mechanical.

## 4. Three concrete changes to ytk most supported by verified literature

1. **Adopt evolutionary clustering with PCM regularization + medoid anchors for profile snapshots** (KDD 2006/2007, TextLuas). Warm-start each `ytk profile` refit from the prior snapshot's centroids, match clusters across snapshots by member-set Jaccard, persist stable theme ids with explicit birth/death/merge/split events. This is the prerequisite for #83 and also fixes silent theme reshuffling in the XML profile itself — today two consecutive `me/profile.md` renders can rank "the same" theme differently for purely artifactual reasons.

2. **Add recency decay to theme weights, with a short-term/long-term split.** Multiply the existing implicit-feedback weight by exp(-lambda*age) per item (RecSys '23, https://arxiv.org/abs/2308.01208 — composes exactly with the confirmed Hu/Koren/Volinsky formulation ytk already uses), and compute each theme's centroid twice: all-time and recent-window (LLM-TUP, https://arxiv.org/abs/2508.08454). The confirmed StreamProfileBench/HorizonBench finding that profiles over-retain stale interests applies to ytk's batch regeneration too — decay is the structural fix, and the refresh prompt should explicitly instruct superseding old evidence rather than accumulating it.

3. **Ground and evaluate the prose portrait.** Two cheap additions: (a) require every `<theme>` claim in `me/profile.md` to cite the vault item ids behind it (personas-2026 https://arxiv.org/abs/2604.26120; GISTBench https://arxiv.org/abs/2603.29112 for groundedness metrics), which also makes the portrait editable-with-consequences in the hub per the confirmed scrutability line (Radlinski 2022, ACL 2024, Co-Authoring the Self); (b) score each regenerated portrait with BUMP's annotation-free eval (https://arxiv.org/abs/2606.05336) — does the profile text rank the user's own held-out ingestions above random ones? That turns "is the new profile better" from vibes into a number.

One documentation fix independent of the above: wherever ytk materials cite the Spotify skip work, correct the venue/DOI (Brost et al., WWW '19, 10.1145/3308558.3313641) and the framing ("implicit feedback", not "weak negative feedback"), and restate the taste-bias-2025 finding in the correct direction (generalists, not niche users, are the poorly-represented case).
